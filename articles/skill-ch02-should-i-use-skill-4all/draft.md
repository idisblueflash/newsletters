# 第二集 一招鲜，吃遍天？
从零设计一个Skill 

多数人的第一个Skill是从网上下的，有人甚至下了几百个Skill。很少有人下载回来还会改，几乎没几个人是从零开始制作Skill。最舒服的椅子肯定是自己造的，尤其是不舒服的地方还能自己改。哪怕我家一把木匠工具都没有，我也是这么倔强地相信着。

即使你不想从头制作Skill，看完个系列，你也能看懂别人Skill的好坏，并且能上手改。

从头制作一个Skill的方法有很多种。有的人直接和Claude说：我们弄一个拼写检查的Skill吧，几轮沟通之后，一个Skill就出来了。还有人直接把找到的知识贴给Claude说：请按这个设计一个检查修辞的Skill，他也能马上得到一个能用的Skill。甚至有人专门设计了一个制作Skill的Skill，每次他要做Skill的时候，就@这个mskill-creator-guide，就能制作一个符合他口味的Skill。更有甚者，有人为了应付老板的要求，把前同事也做成了一个Skill。

我也是这样制作Skill的，直到看见Claude的Skill官方文档，我才发现不是所有的东西都应该做成Skill。


当你手里拿着锤子的时候，看什么都是钉子，总想过去锤几下。但是如果你手里有两个工具，在动手前你就要想想了。

还记得Skill是Prompt的升级版么？它的结构是一个文件夹，下面有个SKILL.md替代Prompt的功能。Claude Code检测到触发词的时候，会把这个Skill完整地加载进来。

如果你在Claude Code里玩了一段时间，你一定对CLAUDE.md这个文件不陌生。这里通常写着你在这个文件夹里Claude做事的规矩。

| 工具           | 什么时候调用 | 适合的情景               |
| -----------   | ------     | ------------------- |
| **CLAUDE.md** | 每轮对话     | 整个项目的规矩、开发偏好、文档风格   |
| **Skills**    | 需要时召唤   | 专业的知识、详细的任务清单、特殊工作流 |

要使用CLAUDE.md，只需在项目的根目录创建一个叫做 CLAUDE.md 的文件，然后在里面写下规则就行了。而如何创建 Skill，我们在后面的章节会一步步来介绍。

下次再想到一个功能，你手上就多了一个工具，应该先想想哪个工具更适合你。

如果你想了解更多的工具，可以看看下面几个对比。

| 工具            | 什么时候调用  | 适合的情景                      |
| ----------- | ------- | -------------------------- |
| **CLAUDE.md**   | 每轮对话     | 整个项目的规矩、开发偏好、文档风格          |
| **Skills**      | 需要时召唤    | 专业的知识、详细的任务清单、特殊工作流        |
| **Hooks**       | 特定条件召唤   | 每次文件存档自动lint、tool呼叫前后的自动动作 |
| **MCP**         | 召唤外面的工具 | 呼叫外部API、数据库                |

如果你觉得上面这四个看起来有点头晕，也不要担心。起码你有了张地图，再遇到事时，不是只用一个Skill硬来。第二，后面两种工具不是这个主题的内容，我们以后有机会再讲。

Hooks 和 MCP 是更进阶的工具，等你把 Skill 和 CLAUDE.md 用熟了，再去探索它们比较好。现在先把前两个看懂就够了。


顺便提一句，选错工具是有代价的：如果把只用一次的临时要求写进 CLAUDE.md，每次你问Claude，它脑子里都会过一遍这些不相干的要求，白白占地方不说，东西多了脑子还容易乱；反过来说，如果把每次对话都需要的规则做成 Skill，次次都要手动触发，会很麻烦，也容易忘。

我在做李笑来老师写作课的多个作业，每次做完练习，我都想把自己的错题收集出来，制作成Anki卡片回顾。Anki是闪卡的电子版本，一面是问题，一面是答案，每天花一刻钟就能练完，时间一久，练习的内容竟然能记住。

问题是：建卡这件事该做成Skill，还是写进CLAUDE.md？

我不只在一个作业里需要建卡，笑来老师后面每一集的作业可能都会用到。这件事跨越了多个对话，而且只在做完练习的最后才触发，不是每次对话一开始就需要它。

相比之下，我还有一个记账的文件夹，每天在里面记花了多少钱。记账只在这一个固定的文件夹里发生，而且每次进入这个文件夹就需要它发挥作用，不需要特别触发。

所以在动手之前，你可以先问自己两个问题：
1. 这件事要在多个不同文件夹里做吗？
2. 这件事只在特定时机触发吗？

两个都是「是」→ 选 Skill；否则选 CLAUDE.md。

如果只有一个「是」，先用 CLAUDE.md。等你真的在第二个地方需要同样的内容，那就是它该变成 Skill 的时候了。比如，建卡规则最初只写在一门课的 CLAUDE.md 里，等到第二门课也需要，把它做成 Skill 就是自然而然的事。

|                | Anki建卡                | 每日记账            |
| ---------- | ----------- | --------------- |
| **作用范围**    | 跨越所有项目         | 一个特定的文件夹        |
| **永远参考规则** | 否。只在建卡时候需要  | 是。每次进入文件夹工作都需要 |
| **触发方式**    | 提到「建卡」的时候载入 | 永远在场，自动识别情景     |
| **工具选择**    | Skill              | CLAUDE.md       |

如果你发现某件事在两三个地方都要用，先做成 Skill。它随时可以触发，比在多个 CLAUDE.md 里复制粘贴更容易维护。

说到这里，我也犯过同样的错。之前有一个文件夹下的 CLAUDE.md 随着时间推移，越来越像一个杂物抽屉：有的负责提交文件，有的负责记账，甚至还有口播审阅这类的废弃流程。直到有一天，我发现在另一个文件夹做类似的文件提交时，又要重新写一遍同样的要求，才意识到：这件事应该做成 Skill，因为它不只属于一个文件夹。

现在打开你自己的 CLAUDE.md，找出一条规则。问问你自己：它真的需要在每次对话都生效吗？还是只在特定任务时才需要？如果是后者，考虑把它拆出来，做成一个 Skill。
