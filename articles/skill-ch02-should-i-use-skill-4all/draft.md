# 第二集 万事皆可Skill嘛
从零设计一个Skill 

很多人用的第一个Skill是从网上下载回来的，有的人甚至下载了几百个Skill。很少有人下载回来还会改skill，更少的人是从零开始设计一个Skill。我个人的体验是，最舒服的椅子肯定是自己造的，尤其是不舒服的地方还能自己改。哪怕我家里没有一把木匠工具，我也这么倔强地相信着。

当然看完这篇文章你即使不想从头设计Skill，也能看懂别人Skill的好坏，并且可以自己上手改。

从头制作一个Skill的方法有很多种。有的人直接和Claude说：我们弄一个拼写检查的Skill吧，接着几轮和Claude沟通之后，一个Skill就出来了。还有人直接把找到的知识贴给Claude，然后说：请按照这个感知传递的原则设计一个检查感知传递的Skill，他也能得到一个马上能用的。甚至有人专门设计了一个制作Skill的Skill，每次他要做的Skill就@这个meta-skill-creator，也能制作出一个符合他口味的Skill。更有甚者，有人把前同事也做成了一个Skill，来应付老板的要求。

我起初也是这样制作自己的Skill，直到看到Claude的Skill官方文档，我才发现不是所有的东西都应该做成Skill。

当你手里拿着锤子的时候，就会看什么都是钉子，总想着去锤几下子。但是如果你手里有两个工具你在动手前就要多想想了。

如果你已经在Claude Code里工作了一段时间，你一定对CLAUDE.md这个文件不陌生。这里通常写着你在这个项目文件夹里做事情的常用规矩。如果把这两个工具写成对比表格，可能会更清晰。

| 工具          | 什么时候调用 | 适合的情景               |
| ----------- | ------ | ------------------- |
| `CLAUDE.md` | 每轮对话   | 整个项目的规矩、开发偏好、文档风格   |
| **Skills**  | 需要时召唤  | 专业的知识、详细的任务清单、特殊工作流 |

要在 CLAUDE.md 里添加规则，只需在项目根目录的 CLAUDE.md 文件里直接写下规则即可；如何创建 Skill，我们在后面的章节会一步步来。

如果你觉得这看起来没什么难度的话，可以再看看下面几个对比。

| 工具          | 什么时候调用  | 适合的情景                      |
| ----------- | ------- | -------------------------- |
| `CLAUDE.md` | 每轮对话    | 整个项目的规矩、开发偏好、文档风格          |
| **Skills**  | 需要时召唤   | 专业的知识、详细的任务清单、特殊工作流        |
| Hooks       | 特定条件召唤  | 每次文件存档自动lint、tool呼叫前后的自动动作 |
| MCP         | 召唤外面的工具 | 呼叫外部API、数据库                |
如果你觉得上面这四个看起来有点晕，也不要担心。因为第一你有了张地图，再遇到事情的时候，不是只用一个Skill硬来。第二，后面两种工具不是这个主题的内容，我们不会讲。

Hooks 和 MCP 是更进阶的工具，等你把 Skill 和 CLAUDE.md 用熟了，再去探索它们。现在先把这两个搞定就够了。

顺便提一句，选错工具是有代价的：如果把只用一次的临时指令写进 CLAUDE.md，它会永久占用每次对话的上下文，造成干扰；如果把每次对话都需要的规则做成 Skill，则每次都要手动触发，容易遗漏。

---
比如我最近在做李笑来老师的写作课里面的感知练习作业。有一个细节要是在一段文字里找出来所有的名词，再标出来抽象名词。这个练习我坚持做了几周了，但是我发现自己仍然会在同样的名词上面犯错。

我早上一直在想这件事，后来发现，我现在只是在做练习，而不是刻意练习。对那些错误的单词，我并没有刻意去回顾。也就是说，我没有一个错题本。

我需要一个做感知练习的错题本，每天回顾。

我每天还在练习一个笔画输入法（仓颉），每个笔画都有专门的闪卡（Anki）来练习。闪卡就和我们小时候学字的卡片差不多，一面是问题，一面是答案。比如正面画着苹果，背面写着「苹果」。 Anki是这种卡片的电子版本。我每天用上一刻钟，几十张这样的卡片就练习完了。而且长期下来，效果真的很好。

我就想着也做一个可以在每次做完练习后，把我的错题收集出来，制作成Anki卡片的Skill。但是我不确认Skill是不是最合适的，因为如果写在CALUDE.md里，似乎也可以做到。

我还有一个记账的文件夹，我在它下面打开了一个Codex（和Claude Code类似的工具），然后每次就在里面写今天花了多少钱，买了什么东西。它就能帮我记录到文件里，后面还能按照分类算出总数，或者能看看我这个月是不是比上个月花多了，甚至可以询问它我这次的同一桶油是不是比上几个月买贵了。

记账的应用看上去更像是CALUDE.md擅长的领域，因为而它的每次对话都会处理这种记账的工作。而我只有在感知练习对话的最后才会召唤制作Anki卡片的工作。

另一个不同是我不会在别的地方记账，只会在固定的文件夹下。而制作Anki卡片这件事我倒是会在不同的对话里调用。比如我可能在下来老师今后的每一节课作业都会制作卡片。

在动手之前，可以先问自己两个问题：① 这件事需要在多个不同项目或文件夹里做吗？② 这件事只在特定时机触发，而不是每次对话都需要吗？两个都是「是」→ 选 Skill；否则选 CLAUDE.md。

于是比较下来，是用Skill还是CLAUDE.md就一目了然了。

|            | Anki建卡      | 每日记账            |
| ---------- | ----------- | --------------- |
| **作用范围**   | 跨越所有项目      | 一个特定的文件夹        |
| **永远参考规则** | 否。只在建卡时候需要  | 是。每次开Session都需要 |
| **触发方式**   | 提到「建卡」的时候载入 | 永远在场，自动识别情景     |
| **工具选择**   | Skill       | CLAUDE.md       |

如果你发现某件事在两三个地方都要用，先做成 Skill。它随时可以触发，比在多个 CLAUDE.md 里复制粘贴更容易维护。

说到这里，我也犯过同样的错。之前有一个文件夹下的 CLAUDE.md 随着时间推移，积累了越来越多不同的内容：有的负责总结提交文件，有的负责记账，甚至还有口播审阅这类的流程。直到有一天，我发现在另一个文件夹做类似的 git 提交时，又要重新写一遍同样的要求，才意识到：这件事应该做成 Skill，因为它不只属于一个文件夹。

---

现在打开你自己的 CLAUDE.md，找出一条规则——它真的需要在每次对话都生效吗？还是只在特定任务时才需要？如果是后者，考虑把它移出来，做成一个 Skill。
