# 如何编写稳定的脚本
和程序员一起 Vibe Coding


## 脚本
Vibe Coding 的新人很少会上来就写「脚本」。一是这个在命令行运行的东西对他们来说很陌生，二是新人都是从设计 Web app 入手的，很晚才会接触脚本。但脚本其实是特别好的入门例子。

脚本就是把按照顺序执行的命令组合在一个文件的东西。你可以理解成那是一个代办清单，只不过里面的每一条代办都可以被计算机直接运行。于是脚本就成了简单又灵活的程序（app）。在 Mac OS 底层，有很多的命令，有的负责获得当前时间，比如`date`；有的负责查看当然有什么文件的，比如`ls`。如果你很好奇他们到底是什么样子的。你可以打开一个叫作 Terminal 的 app（Mac 自带），输入 date 然后回车看看效果。

今天准备要写的是一个「python 脚本」。它和普通脚本最大的不同是组成脚本执行的不是「命令」而是「python 代码」。不过作为新人的你也不用担心，因为这篇文章只会讲思路，你不用学习这些代码细节。

你也可以直接和你的 Codex（AI 编码助手）说清楚你想要做什么，然后让它生成一个 python 脚本。这个办法看起来省事，却会给你在未来几天里带来无尽的麻烦。你会遇到 bug 却完全找不到原因。你不得不推到重来，而你在新版本里却发现有个很有用的功能没写出来。当你再要求 AI 补上这个功能之后，运气好的话，可以一次成功。不好的话，你又会退回到原点从新开始。

今天我们就是要换一种稳健而经典的写法，把这些麻烦永远地避免。


## 中英文混排的例子

让我们用一个简单又不简单的例子开始。


我写博客文章的时候，总是碰到中英文混排的麻烦。

```
现代编辑器（VS Code、Obsidian、文字处理软件）的分词算法基于 Unicode 词边界规则，中英文混接处缺乏空格时，系统无法正确识别词边界，导致快捷键操作越界。
```
上面的 Unicode 这个英文，加在中文之间，看起来很拥挤。我会下意识的手动为它两旁加上空格，就舒服多了。
```
分词算法基于 Unicode 词边界规则
```

这样做还有一个好处，当你习惯了用键盘在文字间做跳转的时候，你可以按下 Option+方向键（Mac OS）在他们之间做方便的跳转、编辑。比如我想修改下面错误的 Unico 拼写，假设我写到了「规则」这个位置，发现前面的 Unico 拼写错了，我就可以按下 Option+左方向键一次，让光标跳到「词」这个字的前面，再按下 Option+删除键把这个错误的单词整个删除，最后重新写出正确的拼写：Unicode。

```
分词算法基于 Unico 词边界规则
```

但是如果让我每次写英文的时候记得要加空格，就难了，我可没有这个习惯。所以我就想设计一个脚本，在我写完的文章上一次性的完成这些操作。

看到这里，你估计已经打开你的 VS Code，叫出 Codex 开始干活儿了。没有想清楚就开始，这是新人最容易范的错误，甚至多年的老程序员也会这样。

## 测试驱动开发

pytest 是用来运行测试的一个 python 包。至于为什么要先写测试而不是 python 脚本，正是这篇文章的重点。

软件编程领域有一个流派是 TDD（测试驱动开发），这个开发方式的特点是，先写测试，再根据测试写代码。这样一步步地把 python 脚本写出来。在「前 AI 时代」，这是业界高标准的做法，但很费力气。在「AI 时代」，这件事做起来就轻而易举。我们正是通过测试来保证 python 脚本的品质的。


## 测试些什么？

我们知道需要在英文左右加上空格，但是这件事远比我们想得复杂。比如我这样问 Claude：

```
让我们限制在文字处理方面，添加空格这件事有那些边界情况？  
```

这是 Claude 的回答：
```
# 中英文混排加空格：文字处理边界情况

**核心规则**：凡是中文字符与半角字符（英文字母、阿拉伯数字）直接相邻处，加空格。

---

## 各类边界情况

### 1. 数字与中文之间

数字是半角字符，与英文字母适用同一规则。

- ❌ `3 个苹果`
- ✅ `3 个苹果`

W3C《中文排版需求》将阿拉伯数字与英文字母等同处理。

---

### 2. 英文紧邻全角标点

全角标点（，。！？）字框本身带有内建空白，视觉上不拥挤。英文左边加空格，右边紧接全角标点不加。

- ❌ `我喜欢 Python，它很简洁`
- ✅ `我喜欢 Python，它很简洁`

。。。
```

目前看就有七种不同的情况，我们可以先做一个简单的情况。在 Codex 里输入：

```
请先写一个单元测试，测试叫做 add-space 的函数可以正确的把中文中的英文两边加上空格。

比如输入「基于 Unicode 词边界规则」，返回「基于 Unicode 词边界规则」

只写测试，然后用 pytest 运行测试
```

这里的单元测试你也可以理解成一个 python 脚本，里面都是测试，稍后我们会看到细节。函数你可以理解成终端下的那些命令，比如你那个黑黑的窗口输入了`date`就能看到今天的日期。而函数做的是类似的事情，你也可以在 python 脚本里组合，拼装这些函数。命令也可以在后面加上内容，比如`ls Desktop`，就是查看目录命令`ls`后面加上了 Desktop 这个文件夹，是可以看到你的桌面上都有哪些内容。有的人的桌面很干净，可能看不到什么，有的人很多，就会出来一大片的结果。

先写测试，是 TDD 的规矩。不用急着写怎么做，而是想清楚要怎么检查。这一点对新人来说有点绕，哪怕是写代码多年的程序员也是如此。但是一旦你转换过来了，后面就会觉得不这么做才不自然。

Codex 的结果：

```
Worked for 20s
已只添加测试文件：tests/test_add_space.py (line 1)

测试内容断言：

add_space("基于 Unicode 词边界规则") == "基于 Unicode 词边界规则"
已运行：

.venv/bin/python -m pytest
当前结果是失败，原因是项目里还没有可导入的 pangu_spacing 模块：

ModuleNotFoundError: No module named 'pangu_spacing'
我没有实现函数，按你的要求只写了测试并运行了 pytest。
```

你会看到这个测试失败了。原因是还没有 pangu_spacing 这个模块，导入失败。这是预料之中的报错，因为我们就让 Codex 写了测试，没有让它写模块和函数。这也是 TDD 的正常甚至是正确的使用方式：先写测试，要看到测试失败，再修复。

这有点像工程上的破坏性测试。如何确定飞机的翅膀可以承受数百吨的压力？那就是要牺牲一架客机，在它的翅膀上用一整排的液压千斤顶去加压，直到它比变形、断裂。

你也可以打开这个测试文件，看看里面到底有什么：
```python
from pangu_spacing import add_space


def test_add_space_adds_spaces_around_english_inside_chinese_text():
    assert add_space("基于 Unicode 词边界规则") == "基于 Unicode 词边界规则"

```
第一行就是导入模块的代码，刚才就是错在在了这里。

def 开始的这一行是函数的名字，它以 test_开头，后面写了要测试的内容。

里面有缩进的一行是具体的测试要求，就是通过了 add_space 函数的这些字，返回来的时候要变成加了空格的字。

> 这里要补充一下函数的用法。它可以接受输入的内容，在这个例子里是一串文字。也可以返回一串处理好的文字。而 add_space("基于 Unicode 词边界规则")的意思是，把那一串文字喂给 add_space，然后获得这个函数的返回字符串。最后拿这个字符串和已经定义好的右边的比较，如果一样，说明这个函数通过了测试。


先写让我们修复这个测试：

```
请用最少的代码，修复这个测试。
然后运行测试。
```

Codex 的返回：
```
Worked for 12s
已用最少代码修复测试，新增 pangu_spacing.py (line 1)，实现 add_space 对中文与英文单词边界加空格。

已运行：

.venv/bin/python -m pytest
结果：1 passed。
```

它新建了一个文件，这正是我们刚才报错找不到的 python 脚本（模块），然后实现了函数 add_space，最后运行了测试：venv/bin/python -m pytest。 1 passed 说明这个测试通过了。我们目前只有一个测试。

如果你这时候你打开 pangu_spacing.py 的文件：

```
import re


def add_space(text):
    text = re.sub(r"([\u4e00-\u9fff])([A-Za-z]+)", r"\1 \2", text)
    return re.sub(r"([A-Za-z]+)([\u4e00-\u9fff])", r"\1 \2", text)

```

第一行 import 它导入了一个 re 的模块，这是 python 内建的模块，所以不会报出：ModuleNotFoundError: No module named 're'的错误。

下面 def 开始是定义了 add_space 函数名字，它还接受一个名叫 text 的输入。

但是后面一大串你肯定就迷糊了，这和咒语没什么分别啊。不过别慌，看到 return 这个词了么。这就是负责把后面的结果返回的。你只要看懂这些就够了。

到这里，我们就完成了一个轮回。从测试，到代码。

在我们开始下一个功能之前，需要先做个提示词的优化。你已经发现我们需要反复的对很多功能执行类似的要求。也就是说，除了功能需求部分会变动，前后的要求是不会变化的。让我们把这个记录在 agents.md 里，让我们后面的 Coding 快起来。

```

```

让我们看看 agents.md 都加了什么：
```
## TDD workflow

When the user provides a feature requirement and asks to develop it with TDD:

1. Add or update the smallest focused pytest test that expresses the requested behavior.
2. Run pytest before changing production code.
3. Confirm the test fails for the expected reason. If it already passes, report that no production change is needed.
4. If it fails, make the smallest production-code change that satisfies the new test.
5. Run pytest again and report the final result.

```

看上去没什么问题，让我们用新的功能试试看：
```
用 tdd 开发下面的功能：

全角括号已提供视觉隔离，括号内壁不需要额外加空格。空格加在括号与外部中文之间。

- ❌ `这个功能（beta）还不稳定`
- ✅ `这个功能（beta）还不稳定`（括号本身隔离，可不加）
- ✅ `这个功能 (beta) 还不稳定`（若使用半角括号，则需加）

```
### 5. 行首或行尾的英文

行首英文前、行尾英文后没有相邻的中文字符，规则不适用，不加空格。

### 6. 连续英文词组与中文接壤

英文词组内部的空格是词组本身的组成部分，不额外处理。只需保证中英交界处有空格。

- ❌ `他是 product manager 职位`

### 7. 专有名词与中文相邻

两个方向均适用，不论英文在左还是在右。

- ❌ `一部 iPhone` / `iPhone 用户`
- ✅ `一部 iPhone` / `iPhone 用户`
