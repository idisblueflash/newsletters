# 什么时候该把计算从 Skill 里拆出来

你以为 AI 在算数，其实它在玩成语接龙. 

就拿我设计的「贝叶斯 Skill」来说，让它预测明天会下雨吗。每次给它一点新内容：温度啊、阴天啊、风速啊，它都会修正自己的判断.

我刚开始的时候偷懒，让 AI 自己推算概率。它推出来分数看着像那么回事，我也没深究。直到有一天我给 Skill 加上了测试，才发现它错得有多离谱。

它不是在「算」下一轮的概率，它是用「猜」的。根据它的训练原理，它会保守地「猜」。它不爱给极端的数字，本该是 0.9 的判断，它会保守地给你 0.75；本该是 0.1 的，它给你 0.25。每一轮都被它往中间拽一点，几轮下来，再多的证据都堆不出一个明确的结论。论文《Evaluating Mathematical Reasoning of Large Language Models》指出，计算错误是 LLM 最难以自查的错误，而 LLM 「猜」出来的平均正确率只有 26.3%。

反正拆成脚本这件事也不用我来做，和 Claude Code 说一句话就成了。要不了几分钟。

有些日常的 Skill 会做确定的工作。比如：刚才贝叶斯例子里的公式计算， 从 PDF 里提取文字，从一个网页里抽出所有的图片链接，把 Markdown 转成 HTML 文件。这种可以找到现成算法（如代码库、经典算法、常用本地 CLI）的， 或者有固定输入输出， 每次同样输入得到同样输出的过程，都适合让 Claude Code 拆出来做成脚本，再让 Skill 调用。 

如果你不清楚这里有没有「确定性」的功能，你也可以把这篇文章丢给 AI，让它自己找。如果你能碰到那种即确定又多次被调用的功能，你就挖到宝了。这种高频功能做成脚本，不仅能为你节省大量的 Token，而且能让你的 Skill 更快。这也是 Antropic 官方 Skill 创建脚本里的推荐做法。

如果你只是盯着那种反复使用的功能拆，你可能会漏掉另一种「脆弱操作」的情况。假设你正在一条长长的吊桥上，两边是深不见底的悬崖。你不敢往下看，只能用双手抓紧两旁又粗又扎手的麻绳，慢慢地往前挪步。山谷里的强风会把吊桥吹得晃来晃去，你的心脏也会跟着晃来晃去。你迈出的每一步都会小心翼翼。

日常工作里也有这种「脆弱操作」的情况，比如修改数据库结构之后的迁移操作就是这样。你需要按照固定的先后顺序操作，而通常也只有这么一条正确的路。如果让 AI 随着自己的性子自由发挥，你后面根本没办法用 Ctrl+Z 来补救。就像是一封重要的邮件发出去之后，就很难再撤回。

还有一类是「让脚本来管理进度」的情况，Skill 同样没有办法记住一套流程的正确顺序，它可能会跳步，不按照你要求的顺序执行或自己添加一些不存在的步骤。限于篇幅的关系，这里就不展开说了。如果你有需要，请来信，我会单独写一篇。

遇到一个 Skill，先问有没有确定答案；有的话再问会不会出错；出错了会不会难以恢复。这三个问题，任意一个答「是」，就是拆脚本的信号。

反过来，有些东西不该拆。那些需要理解上下文、灵活判断、或者本来就在处理模糊输入的工作，正是 LLM 的主场。比如「根据用户的语气决定回复的风格」，或者「判断这段话的意思是什么」，这种事情没有固定答案，也找不到现成算法，拆成脚本反而什么都做不了。规则是：有确定答案的交给脚本，没有确定答案的留给 LLM。

当然也不能无止境地多拆。另一篇论文《Less is More：Optimizing function call for LLM Execution onEdge Devices》分析了为什么过多的脚本调用会让 LLM 的脑子变得不太灵光。选择性地减少可以调用的脚本的数量，会让执行时间最多缩减 70%。这同样适用在 Skill 拆出脚本的情况。告诉 AI 按照这种原则拆脚本就好。

罗马不是一天造成的。Skill 也不是一上来就要先拆出来脚本。实际的做法是「没问题就不动它」。让真实的案例倒逼 Skill 的改进，永远是防止过度设计的良方。比如你先让 Claude Code 设计一个纯 Prompt 的 Skill，通常 Claude Code 会默认这么做。后面碰到了每次「输出不一致」的问题，才升级到拆脚本。拆出来的脚本最好是 Python 3 + 内置库，因为每台 Mac 电脑都预装了这些环境。你从自己的 Mac Book Air 换到家里另一台的 Mac Mini ，你的 Skill 也能正常使用。

回想一个你常用的 Skill，是不是有过上面提到的那些情况，如果是，就看看能不能拆出脚本来。

让 LLM 的归 LLM，让脚本的归脚本。
