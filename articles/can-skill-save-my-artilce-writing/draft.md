# Codex 写文章越写越跑偏，要改用 Skill 嘛？
还是应该转用 Claude？

E小姐是 SEO 文章的编写者。他的日常流程是从关键词开始的。选出需要写文章的主题关键词，放进谷歌搜索引擎，把前十名的文章下载回来，让 Codex 分析。然后写出新文章的架构，再由E小姐来审核架构，确认之后 Codex 开始正是写文章。

她把文章架构、写作规范整理成 .md 文章喂给 Codex 写文章，一开始出来的内容还算符合要求，但是随着一直按照流程往下进行，加上中间的确认和人工指导，在这个对话的后面经常出现几个问题：
- 文章结构架构不一致
- 开头写法跑掉
- 文章语气和范例越查越多

她想问，建立一个 Skill 是不是就能解决这个问题？把 SEO 文章的规范写在 Skill里，而不是每次只依靠 .md 文件？

她还有一些其他的疑问：
1. 是不是因为她每次都把所有规则放在同一个 Project Context 里？
2. 是不是应该用 Skill 来固定 SEO 写作规范？
3. 还是说其实 Claude 比较适合长文的 workflow？

## 上下文腐烂的味道
她已经把规范整理成了.md文件，放入了Codex，我们假设这是放入了Codex的对话窗口（session）。比如 @rules.md 让Codex去读这个规范；或者作为附件给了 Codex。而且她也看到了刚开始生成的内容「还算符合要求」。那么证明这个规范起作用了。

但是如果她下一次新开了对话窗口，要么她需要再像上面一样导入一次这些规范，要么把它们打包成一个skill。Skill 可以在人们用它的时候自动导入规范，这只是让她免去了手工指定规范文件的动作，的确能便利很多。

而「后面开始常出现」的各种问题说明，这是和时间有关的「退化」现象，闻起来是「上下文腐烂」（Context Rot）的味道。这是在去年被正是命名的一个概念。随着输入内容（token）的增长，模型的准确度会下降。比如在 200K token 的窗口内，50K 的用量就已经出现了 30%+ 的准确度下降。这会导致一些具体的表现：AI 不再紧盯着中间部分的内容看，有更多内容的让它分心。上下文腐烂的核心机制是：模型在超长对话里会把注意力分散到所有内容，而不是死盯着最初给的规范。规范还在，但它的权重被稀释了。

如果每次分析的文章（比如前十篇）内容很长，又需要多轮人工讨论来更正的情况下，就很容易让对话里的内容飞速增长。更别说她每天写的不同文章都要在同一个对话框里跑了。

一些 SEO AI 工作流的文章觉得「只要有 Skill 或 提示词 就够了」这种想法并不够。他们强调一种组合的多次干预。比如增加几个范例（few-shot），还有模板。

所以单靠把规范打包成 Skill 是不够的，Skill 解决的是「每次要手动导入规范」的麻烦，但解决不了「对话太长、注意力被稀释」的问题。

## 比较稳妥的建议

她的问题出在两个地方：一是把分析文章和正式写文章都堆在同一个对话里，二是跨天写不同文章也不开新窗口，让 token 量持续累积。

- 换成 Skill ，还要优化
    1. 把现有的 .md 规范文件打包成 Skill，每次在新对话的时候可以自动注入
	    - 只要 @rules.md 然后和 Codex 所，请把这些规范设计成一个 Skill
    2. 在 Skill 中附带 2-3 篇历史优质文章的节选（开头段落、核心结构段落），作为 few-shot 范例
    3. 写作提示中加入：「请在输出文章前，对照上面的范例的开头写法和标题等规则自查一遍」

- 缩短上下文，防止腐烂
	1. 把「文章分析 到 架构生成」与 「正式写文章」拆开为两个独立的对话。可以缩短每次对话的上下文长度。
    2. 甚至为这两个流程分别设计 Skill，可以减轻 Skill 注入时候的 token 用量
	    - 不需要的 Skill 不要一起导入
        
- 在输出文章之后还要验证
    1. 每篇文章写完后，用一个额外的提示做「规则符合度检查」。比如：「对照一下规范清单，指出哪些段落偏离了规范并给出修改建议」。
    2. 创建一个「问题模式纪录表」，记录一些模型不按照要求输出的例子，积累一定的数量，再对 Skill 进行更新。

## 回答刚才的问题
> 1. 是不是因为她每次都把所有规则放在同一个 Project Context 里？

有可能。要看她的规则长度。如果太长，把不同阶段拆分成不同 skill，能解决。但我推测她的上下文主要是被那些需要分析的文章们撑爆了。


> 2. 是不是应该用 Skill 来固定 SEO 写作规范？

是。固定下来更方便，最好按照阶段分拆为不同的 Skill。比如文章结构生成和写文章可以分成两个Skill

> 3. 还是说其实 Claude 比较适合长文的 workflow？

不是。所有模型都有这个问题。她现在的问题出在流程上，暂时不用换。不过 Claude 对文章撰写的确跟擅长，以后可以考虑。
