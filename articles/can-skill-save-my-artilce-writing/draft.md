# Codex 写文章越写越跑偏，要改用 Skill 嘛？
还是应该转用 Claude？

E小姐是 SEO 文章的编写者。她的日常流程是从关键词开始的。选出要写文章的主题关键词，放进谷歌搜索，把前十名的文章下载回来，让 Codex 分析。然后指导 Codex 写出新文章的架构，再由E小姐来审核架构，确认之后 Codex 开始正式写文章内容。

她把文章架构、写作规范整理成 .md 文章喂给 Codex ，一开始写出来的内容还算符合要求，但是一路按流程跑下去，加上中间的确认和人工指导，对话的后面经常出现几个问题：
- 文章结构越写越乱：第三篇开始少了「常见问题」段落，第五篇又多出一个没在架构里的小标题
- 开头写法跑掉：本来约好用问句开头，后面几篇悄悄换成了「在当今数字营销时代……」
- 文章语气和范例越来越远：一开始还在模仿范例的简洁口吻，到后面出现了「综上所述」和「值得关注的是」

她想问，建立一个 Skill 是不是就能解决这个问题？把写作规范裹在 Skill 里，而不是每次给 .md 文件？

她还有一些其他的疑问：
1. 是不是因为她每次都把所有规则放在同一个 Project Context 里，才会这样？
2. 是不是应该用 Skill 来固定 SEO 写作规范？
3. 还是说其实 Claude 比较适合长文写作的 workflow？

## 上下文腐烂的味道
她已经把规范整理成了.md文件，放入了Codex，这里我们就当成是放进了 Codex 的对话窗口（session）。比如 @rules.md 让 Codex 去读这个规范；或者作为附件给了 Codex。而且她也看到了刚开始生成的内容「还算符合要求」。

但是她下次开了新的对话窗口，要么再像上面一样导入一次这些规范，要么把它们打包成一个skill。Skill 可以在需要的时候自动导入规范，这只是让她免去了上传规范文件的动作。

「后面开始常出现」的那些问题，说明这是和时间有关的「退化」现象，闻起来是「上下文腐烂」（Context Rot）的味道。这是去年才被正式命名的一个概念。随着输入内容（token）的增长，模型的准确度会下降。比如在 200K token 的窗口内，50K 的用量就已经出现了 30%+ 的准确度下降。这会导致一些具体的表现：比如第三篇还在乖乖用问句开头，到了第五六篇，这条规定已经悄悄消失了。上下文腐烂的核心机制是：模型在超长对话里会把注意力分散到所有内容，而不是死盯着最初给的规范。规范还在，但它的权重被稀释了。

如果每次分析的文章（比如前十篇）内容很长，又需要多轮人工讨论来更正，就很容易让对话里的内容飞速增长，一个来回下来 token 用量轻松过 50K，还没到第三篇文章就已经开始腐烂了。更别说她每天写的不同文章都要在同一个对话框里跑了。

有些研究 SEO AI 工作流的文章认为「只要有 Skill 或 提示词 就够了」这种想法并不够。这些文章强调一种组合的多次干预。比如增加几个范例（few-shot），还有模板。

所以单靠把规范打包成 Skill 是不够的，Skill 解决的是「每次要手动导入规范」的麻烦，但解决不了「对话太长、注意力被稀释」的问题。

## 稳妥的建议

她的问题出在两个地方：一是把分析文章和正式写文章都堆在同一个对话里，二是写不同文章也不开新窗口，让 token 量持续累积。

- 先换成 Skill ，还要优化
    1. 把现有的 .md 规范文件打包成 Skill，每次在新对话的时候可以自动注入
	    - 只要 @rules.md 然后和 Codex 说，请把这些规范设计成一个 Skill
    2. 在 Skill 中附带 2-3 篇历史优质文章的节选（开头段落、核心结构段落），作为 few-shot 范例
    3. 写作提示中加入：「请在输出文章前，对照上面的范例的开头写法和标题等规则自查一遍」

- 再缩短上下文，防止腐烂
	1. 把「文章分析 到 架构生成」与 「正式写文章」拆开为两个独立的对话。
    2. 甚至为这两个流程分别设计 Skill，可以减轻 Skill 注入时候的 token 用量
        
- 最后输出文章之后要验证
    1. 每篇文章写完后，用一个额外的提示做「规则符合度检查」。比如：「对照一下规范清单，指出哪些段落偏离了规范并给出修改建议」。
    2. 创建一个「问题模式纪录表」，记录一些模型不按照要求输出的例子，积累一定的数量，再对 Skill 进行更新。

## 回答刚才的问题
> 1. 是不是因为她每次都把所有规则放在同一个 Project Context 里？

有可能。要看她的规则长度。如果太长，把不同阶段拆分成不同 skill，能解决。


> 2. 是不是应该用 Skill 来固定 SEO 写作规范？

是。固定下来更方便，最好按照阶段分拆为不同的 Skill。

> 3. 还是说其实 Claude 比较适合长文的 workflow？

不是。她现在的问题出在流程上，而不是模型，暂时不用换。不过 Claude 对文章撰写的确更擅长，以后可以考虑。
